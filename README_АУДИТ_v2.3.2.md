## 2. Дефект 1: нетерминальная SELL-заявка

**Где:** `main.py::_try_resolve_absent_position()`, ветка В2 (закрытие по своей
SELL-заявке из реестра).

**Дефект v2.3.1.** Ветка В2 уточняла статус/исполнение/цену заявки у брокера,
но после уточнения проверяла только `executed <= 0`. Если запись реестра или
отчёт брокера давали `executed_lots > 0` при НЕТЕРМИНАЛЬНОМ статусе
(`NEW`, `PARTIALLYFILL`, неизвестный статус), учёт позиции немедленно
закрывался (`LEDGER_CLOSE`) по частично исполненной **живой** заявке: исполнение
могло продолжиться или быть отменено уже после закрытия локального учёта.

**Исправление.** Окончательным исполнением считается только терминальный
статус (`FILL`, `CANCELLED`, `REJECTED`, `EXPIRED` — `_TERMINAL_ORDER_STATUSES`).
После уточнения статуса у брокера добавлена проверка: если статус
нетерминальный (в том числе при `executed_lots > 0`), функция возвращает новое
действие `"uncertain"`:

- локальный учёт **не закрывается** (никакого финального закрытия);
- позиция переводится в `UNCERTAIN`; подтверждённые per-order cursor'ом лоты
  сохраняются (частичное исполнение учтётся штатно через `resolve_closing`);
- повторная отправка SELL **не выполняется** (заявка уже в реестре; SL/TP для
  UNCERTAIN не действуют — новых close-заявок нет);
- новые входы блокируются: `client.uncertain_state = True` + запись в
  `mismatches` reconcile (`reconcile_done = False`);
- событие `SELL_NON_TERMINAL_CLOSE_BLOCKED` в журнал исследований + notify;
- разрешение — только терминальный отчёт этой заявки: следующий вызов В2
  закроет учёт с подтверждённой ценой (`FILL`/`CANCELLED`/`EXPIRED` с
  `executed_lots > 0`) или достоверный отказ без исполнения уводит позицию
  в механизм В3.

**Требование ТЗ «при невозможности достоверно определить окончательное
состояние — UNCERTAIN»** выполняется и для противоречий: если реестр говорит
`FILL`, а брокер отвечает `NEW`/ошибка, статус после уточнения остаётся
нетерминальным — учёт не закрывается (fail-closed).

**Тест:** `test_defect1_sell_partialfill_absent_no_final_close` — SELL на
10 лот., исполнено 3, статус `PARTIALLYFILL`, позиция у брокера отсутствует.
Проверено: локальное окончательное закрытие запрещено (`quantity` уменьшен
только на 3 подтверждённых cursor'ом лота, состояние `UNCERTAIN`), повторной
SELL нет, входы заблокированы; при достижении заявкой `FILL` (10 лот.) учёт
закрывается штатно с реальной ценой.

## 3. Дефект 2: обход двойного подтверждения через UNCERTAIN

**Где:** `execution.py::ExecutionMonitor.resolve_uncertain()` и
`main.py::process_closing()`.

**Дефект v2.3.1.** `resolve_uncertain()` при отсутствии позиции у брокера
(`broker is None`) немедленно закрывал учёт по **одному** достоверному снимку
(`CLOSED`, `EXTERNAL_CLOSE`, `exit_price_confirmed=False`). Это обходило
механизм В3 (два достоверных снимка с минимальным интервалом
`RECONCILE_CONFIRM_MIN_AGE_SECONDS`) и закрывало учёт, пока исход собственной
SELL-заявки не подтверждён. `process_closing` вызывал `resolve_uncertain` для
всех UNCERTAIN-позиций перед сверкой — обход срабатывал систематически, в том
числе когда собственная SELL ещё жива (`NEW`/`PARTIALLYFILL`) или её отчёт
недоступен.

**Исправление.** `resolve_uncertain()` при отсутствии позиции у брокера учёт
**не закрывает** — позиция остаётся в `UNCERTAIN`. Проверены все пути закрытия
UNCERTAIN-позиции; после исправления закрытие возможно только тремя
способами:

| Путь | Условие | Где |
|---|---|---|
| Собственная SELL — отчёт заявки | Терминальный статус close-заявки, per-order cursor, реальная цена | `process_closing → resolve_closing → apply_close_execution` |
| Собственная SELL — В2 | Достоверный **терминальный** отчёт реестра/брокера (после Дефекта 1 — только терминальный) | `reconcile → _try_resolve_absent_position` (В2) |
| Внешнее закрытие — В3 | **Два** достоверных снимка «позиции нет» с интервалом ≥ `RECONCILE_CONFIRM_MIN_AGE_SECONDS`; первый снимок только регистрирует кандидата | `reconcile → _try_resolve_absent_position` (В3) — **единый механизм** |

Дополнительно:

- `get_positions() = None` (недостоверный снимок) **не подтверждает и не
  сбрасывает** подозрение: `process_closing` при `None` не вызывает
  `resolve_uncertain`, `reconcile` при `None` выходит до ветки кандидатов —
  `_external_close_candidates` не трогаются, таймер интервала не
  перезапускается;
- сохранена возможность закрытия по достоверному терминальному отчёту
  собственной SELL-заявки (пути 1 и 2 в таблице);
- P0-5 (`_uncertainty_resolved_by_reconcile`, маркер последней успешной
  сверки), OrderLedger, per-order cursor и fail-closed не ослаблены;
  `order_ledger.py` не менялся;
- повторная отправка SELL невозможна на любом пути: SL/TP действуют только на
  `OPEN` (`check_all`), `close_position` для UNCERTAIN не вызывается, В2/В3
  заявок не отправляют.

**Интеграционные тесты** (`tests/test_v232_close_defects.py`, полный цикл
`trading_cycle`, единый механизм В3, реестр, state.json, CSV):

| № | Сценарий | Результат |
|---|---|---|
| 1 | UNCERTAIN без `close_order_id`, позиция исчезла | Цикл 1 — только кандидат В3, учёт не тронут; цикл 2 (второй снимок, разнос ≥ 30 c) — `EXTERNAL_CLOSE`; цикл 3 — CSV без P&L |
| 2 | UNCERTAIN с SELL `PARTIALLYFILL` (3 из 10), позиция исчезла | Окончательное закрытие запрещено (`UNCERTAIN`); при терминальном `CANCELLED` (3 лот.) — закрытие по терминальному отчёту с реальной ценой (В2 сохранён) |
| 3 | UNCERTAIN с SELL `NEW`, позиция исчезла | Мгновенного закрытия нет, повторной SELL нет; закрытие — двойное подтверждение В3 |
| 4 | UNCERTAIN с SELL `REJECTED`, позиция исчезла | Возврат в `OPEN` (отказ без исполнения), кандидат В3; закрытие после двух снимков; обречённых повторных SELL нет |
| 5 | `get_positions()=None` между двумя подтверждениями | Кандидат сохранён с прежним `first_seen` (ни подтверждает, ни сбрасывает); следующий достоверный снимок подтверждает В3 |
| 6 | Рестарт между первым и вторым подтверждением | Мгновенного закрытия после рестарта нет: кандидаты не персистятся (консервативно), двойное подтверждение начинается заново |
| 7 | Повторный отчёт об исполнении после разрешения ситуации | Per-order cursor идемпотентен: «воскрешения» нет, повторного применения нет, дубль CSV не пишется |

**Верификация тестов:** на коде v2.3.1 (до исправлений) падают 5 из 8 —
D1, 2.1, 2.2, 2.5, 2.6 (те, что покрыывают обход двойного подтверждения и
нетерминальную SELL). Тесты 2.3, 2.4, 2.7 — регрессионные guard'ы требуемого
поведения (проходят и до, и после исправления).

## 6. Готовность к песочнице

Оба блокирующих дефекта аудита v2.3.1 устранены и покрыты тестами. Заявление
о готовности к полевому запуску в песочнице **сознательно не делается**:
решение о запуске — за оператором после проверки сборки (SHA256, diff, журналы
тестов) и подтверждения окружения (SDK, `pandas_ta_classic`, доступ к
SANDBOX), поскольку 25 окружение-зависимых падений в этой среде не воспроизводят
конфигурацию рабочего узла.
