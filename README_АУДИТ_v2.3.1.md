# Tsclp_v2.3.1-stage1 — отчёт аудита ТЗ v2.3 и пакет исправлений

Полная сборка на замену. База: `tsclp_v2.3_stage1`. Изменены **3 файла кода
(config.py, execution.py, main.py)** и **3 тестовых файла**, добавлен
**1 новый интеграционный тест**. Остальные файлы — точные копии v2.3
(order_ledger.py, logger.py, strategy.py, risk_manager.py, screener.py,
tinkoff_client.py, telegram_bot.py, утилиты — БЕЗ изменений).

## Ответы на пункты ТЗ (аудит Tsclp_v2.3_stage1)

### ТЗ-1. Почему ручное закрытие не вызывает reconcile в штатном trading_cycle

**Причина найдена.** В v2.3 `reconcile()` вызывался только в трёх случаях:
(a) `client.is_uncertain()`, (b) в конце `process_closing` при наличии
UNCERTAIN-позиций, (c) на старте. Ручная продажа в приложении брокера **не
выставляет ни один из этих флагов**. Пакет В2/В3 живёт ВНУТРИ reconcile —
и в штатном цикле не срабатывал вообще. Фантомная OPEN-позиция продолжала
мониториться; при срабатывании SL/TP робот отправлял SELL, который брокер
отклонял (позиции нет), `resolve_closing` возвращал позицию в OPEN — цикл
обречённых заявок; расхождение обнаруживалось только после рестарта
(стартовый reconcile) — ровно то, что наблюдалось в поле.

**Исправление:** в v2.3.1 `reconcile()` выполняется **в каждом штатном цикле**
(шаг 4 trading_cycle). Стоимость — один `get_positions()` за цикл (шаг 6 и
так делает такой же вызов перед входами). Порядок остальных шагов не менялся.

### ТЗ-2. Обнаружение исчезновения по достоверному снимку брокера

Обеспечено безусловным reconcile (см. ТЗ-1). Достоверность — как прежде:
`get_positions() = None` (ошибка/неполный снимок) → учёт НЕ меняется,
сверка не завершена (fail-closed D5, без изменений).

### ТЗ-3. Двойное подтверждение В3 сохранено и усилено

1. Подтверждение принимается не раньше, чем через
   `config.RECONCILE_CONFIRM_MIN_AGE_SECONDS` (по умолчанию =
   `TRADING_CYCLE_SECONDS` = 30 с) после первого обнаружения. Два reconcile
   в ОДНОМ цикле (process_closing + шаг 4) подтверждением не считаются.
2. **Новое:** кандидат на внешнее закрытие снимается, если позиция снова
   видна у брокера (`EXTERNAL_CLOSE_SUSPECT_CLEARED`). Без этого «протухший»
   first_seen дал бы мгновенное подтверждение при БУДУЩЕМ исчезновении
   позиции по одному снимку — двойное подтверждение потеряло бы смысл.
3. Недостоверный снимок (`None`) подтверждением не является: reconcile при
   None выходит до логики кандидатов, кандидаты не трогаются.
4. Неразборчивая метка времени первого обнаружения подтверждением не
   является (консервативно).
5. Кандидаты не персистятся (как и прежде): рестарт начинает двойное
   подтверждение заново — два свежих достоверных снимка.

### ТЗ-4. Частичное исполнение SELL и корректность финансового учёта

**Проверено, механизм не ослаблен:**
- per-order курсор `apply_close_execution`: применяется только новый
  cumulative delta именно этой заявки; противоречивый cumulative →
  UNCERTAIN + fail-closed;
- частичный терминальный SELL → остаток позиции остаётся OPEN и
  мониторится; FILL при executed<requested → UNCERTAIN → синхронизация
  по снимку брокера;
- В2 при частичном исполнении закрывает учёт только по подтверждённым
  лотам с реальной ценой, остаток — с пометкой «остаток закрыт вне
  робота» в error_note (тест `test_v2_partial_sell_closes_only_proven_lots`).

**Найден и устранён дефект учёта (пересечение с ТЗ-5):** UNCERTAIN-позиция
с своей close-заявкой раньше НЕ опрашивала отчёт заявки при разрешении и
закрывалась по снимку с фиктивным P&L (exit = entry или 0.0). Теперь
`process_closing` сначала разрешает её через `resolve_closing` (отчёт
заявки) — если SELL исполнился офлайн, учёт закрывается с РЕАЛЬНОЙ ценой
исполнения. Если отчёта нет/без цены — ТЗ-5 (ниже).

### ТЗ-5. Запрет фиктивного P&L при неизвестной цене исполнения

**Дефект v2.3:** `process_closing` писал `exit_price = pos.execution_price
or 0.0` — при неизвестной цене исполнения в CSV попадал фиктивный P&L:
- В3: fallback 0.0 → «убыток» размером в полную стоимость позиции;
- `resolve_uncertain` (позиция исчезла при UNCERTAIN): exit = цена входа →
  фиктивный «нулевой» P&L;
- В2/штатное закрытие при отчёте без цены: exit 0.0 → тот же фиктивный убыток.
Всё это искажало `cumulative_net_pnl_rub`.

**Исправление:** новое поле `TrackedPosition.exit_price_confirmed`
(персистится в state.json; старый state.json → False):
True — ТОЛЬКО когда цена взята из реального исполненного close-ордера
(отчёт брокера / реестр В2). В3 (приблизительная рыночная цена) → False —
цена ручной продажи неизвестна, P&L не выдумывается.
CSV при неподтверждённой цене: строка пишется (сделка не теряется) с
ПУСТЫМИ полями exit_price/commissions/slippage/gross/net/cumulative и
пометкой `PRICE_UNKNOWN` в error_note; cumulative не изменяется
(`get_cumulative_net_pnl` пропускает пустые net_pnl_rub). Telegram-уведомление
без выдуманных цифр. Событие `CLOSED` получает `pnl_recorded: false`.

### ТЗ-6. Ослабления защит — НЕТ

- `order_ledger.py` — **не изменялся** (append-only, идемпотентность INTENT,
  fail-closed целостность журнала);
- UNCERTAIN-логика и P0-5 (`_uncertainty_resolved_by_reconcile`,
  маркер `_last_reconcile_confirmed_utc`) — не изменялись;
- защита от повторного применения лотов (per-order cursor, `closed_entry_order_ids`,
  guard `register_executed_buy`) — не изменялась;
- fail-closed гейты шага 5 (trading.flag, reconcile_done, monitoring_error,
  state_save_failed, недостоверный реестр, заявки без FIGI) — не изменялись;
- изменения В3 (min-age + очистка кандидатов) — УСИЛЕНИЕ, не ослабление;
- периодический reconcile использует ту же функцию reconcile с прежними
  гарантиями (None → учёт не меняется; адопция → RECOVERY с блокировкой BUY).

### ТЗ-7. Интеграционный тест полного trading_cycle (ручная продажа)

Новый файл `tests/test_manual_close_integration.py` — полный `trading_cycle`
на фейковом брокере (без сети, только SANDBOX-семантика):
1. `test_integration_manual_sell_full_trading_cycle` — ручная продажа:
   цикл 1 — обнаружение (кандидат, учёт не тронут, заявок нет), цикл 2 —
   двойное подтверждение → EXTERNAL_CLOSE, цикл 3 — CSV без фиктивного
   P&L; state.json обновляется в конце каждого цикла (В1);
2. `test_integration_unreliable_snapshot_is_not_confirmation` — снимок None
   не подтверждает и не сбрасывает кандидата;
3. `test_restart_closing_position_sell_filled_offline` — рестарт с CLOSING,
   SELL исполнился офлайн → реальная цена + P&L, БЕЗ повторной отправки;
4. `test_restart_sell_rejected_position_absent_no_false_close` — SELL
   отклонён + позиция исчезла → НЕ мгновенное закрытие: сначала кандидат В3,
   затем двойное подтверждение (защита от ложного закрытия);
5. `test_restart_open_position_alive_no_reopen` — живая позиция → учёт не
   меняется, повторного открытия нет, заявок нет;
6. `test_restart_uncertain_with_own_sell_filled_gets_real_price` — UNCERTAIN
   + свой SELL исполнен офлайн → реальная цена вместо фиктивного P&L;
7. `test_quiet_cycle_updates_state_json` — тихий цикл обновляет state.json,
   переход CLOSING сохраняется (В1).

## Суть правок кода

**config.py**
- `BUILD_VERSION = "v2.3.1-stage1"` (трассируемость журнала по сборке);
- `RECONCILE_CONFIRM_MIN_AGE_SECONDS = TRADING_CYCLE_SECONDS` (ТЗ-3; код
  использует getattr — старый config.py без константы совместим).

**execution.py**
- `TrackedPosition.exit_price_confirmed` (конец dataclass; `from_dict`
  setdefault False — совместимость со старым state.json);
- `apply_close_execution` ставит маркер по `avg_exec_price`;
- `resolve_uncertain` (позиция исчезла у брокера): close_reason
  EXTERNAL_CLOSE (если не задан), error_note, маркер False — P&L не
  выдумывается.

**main.py**
- шаг 4 trading_cycle: `reconcile()` в каждом цикле (ТЗ-1/2);
- В3: min-age guard подтверждения + очистка кандидата при возврате позиции
  у брокера + расширенная телеметрия событий (ТЗ-3);
- В2: пометка «цена не получена — CSV без P&L» + `price_confirmed=True`
  (цена из реального ордера) (ТЗ-4/5);
- `_finalize_position_closed(..., price_confirmed=...)` — единая точка
  выставления маркера (В3 → False, приблизительная цена);
- `process_closing`: UNCERTAIN с close_order_id сначала разрешается по
  отчёту заявки (`resolve_closing`) — реальная цена «офлайн»-исполнения
  (ТЗ-4); CSV-блок: при неподтверждённой цене — пустые финансовые поля +
  `PRICE_UNKNOWN`, cumulative не тронут; события/уведомления без выдуманных
  цифр (ТЗ-5).

**Тесты**
- `test_stage1_packet_v.py`: В3-тесты обновлены под min-age (два вызова
  подряд не подтверждают); добавлены: reject неразборчивой метки,
  подтверждённость цены В2, частичный SELL (только подтверждённые лоты),
  снятие кандидата при возврате позиции у брокера;
- `test_main_helpers.py` / `test_fail_closed.py`: setup имитирует
  подтверждённую цену (`exit_price_confirmed=True`) — семантика ТЗ-5
  (без маркера P&L не рассчитывается);
- `test_manual_close_integration.py` — новый (см. ТЗ-7).

## Полевой чек-лист (дополнение к чек-листу v2.3)

1. [ ] `pytest tests/ -v` — как в v2.3 (падения legacy-тестов вне окружения
       репозитория — ожидаемы, сравнить список с `РЕЗУЛЬТАТЫ_ТЕСТОВ.txt` репо).
2. [ ] Ручная продажа одной позиции при работающем роботе → в логе:
       `[reconcile] ... подозрение на внешнее закрытие` (учёт не тронут) →
       через ~30 с `[reconcile] внешнее закрытие подтверждено повторной
       сверкой` → `POSITION_CLOSED_EXTERNAL` → CSV-строка с пустыми P&L и
       пометкой PRICE_UNKNOWN. Никаких SELL-заявок по фантомной позиции.
3. [ ] Продажа в момент активной заявки робота → `POSITION_CLOSED_BY_LEDGER`
       с реальной ценой (В2) — как в v2.3, теперь срабатывает и БЕЗ рестарта.
4. [ ] `state.json` обновляется в конце каждого цикла (проверка mtime) — В1.
5. [ ] Позиция исчезла и вернулась (песочница) → `EXTERNAL_CLOSE_SUSPECT_CLEARED`
       в событиях, учёт не закрывается.

## Честные ограничения (не закрыты этой версией)

- Пока робот офлайн, SL/TP не существуют на бирже (архитектурный вопрос
  биржевых стоп-заявок — отдельный этап). Минимум: авторестарт процесса.
- В3 закрывает учёт с пустым P&L (цена ручной продажи неизвестна) — это
  осознанно, по ТЗ-5. Если понадобится оценка — только отдельным
  операторским решением, не автоматикой.
- Остаточный кейс из v2.3 сохранён: UNCERTAIN без close_order_id и без
  исполнения (executed_lots=0) → CSV не пишется (прежднее поведение).
- Редкий модельный нюанс: при частичном В2-закрытии модельная (не
  фактическая) комиссия входа считается по подтверждённым лотам выхода.
  При фактических комиссиях входа (обычный случай) расчёт точен.
